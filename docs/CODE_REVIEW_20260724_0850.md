## 1. 전체 구조 요약

```
firmware/stm32f0/   ← STM32 C 펌웨어
    vfd_scan.c/.h        [코어] 43페이즈 스캔 패커 + 240비트 emit (HAL 무의존)
    vfd_host_link.c/.h   [코어] 패킷 수신, CRC, 더블버퍼 (HAL 무의존)
    vfd_delay.c/.h       [코어] 경험적 지연 루프 (HAL 무의존)
    GT20L_Font.c/.h      [데모] framebuffer blitter + 폰트
    font.c, vfd_framebuffer.c  [데모] 데모용 정적 이미지
    main.c               [보드글루] GPIO 직접 제어, TIM14 ISR 협력, HAL 의존
    stm32f0xx_it.c       [보드글루] NMI/HardFault/TIM14 핸들러

src/mn12832l/        ← Python 호스트 스택
    protocol.py          [공유계약] 와이어 포맷 (C vfd_host_link.h와 1:1)
    renderer.py          MVLSB 512바이트 프레임버퍼 어댑터
    transport.py         SubprocessTransport (serial bridge 자식 프로세스)
    serial_bridge.py     pyserial stdin/stdout 프록시
    display.py           VfdDisplay (dedup + sequence + CRC + retry)
    twin.py              DigitalTwinTransport + 핀 trace 복원 + TUI/CLI

src/mn12832l/menu/   ← Tkinter 메뉴 미리보기 (MVP)
    input.py             InputEvent + InputSource(ABC) 추상화
    model.py             MenuModel 순수 상태머신
    render.py            Screen → 512바이트 프레임 렌더
    presenter.py         MenuPresenter (model + display + twin 연결)
    tk_source.py         TkinterSource (InputSource 구현체)
    app.py               Tkinter 창 + 메인 루프
    __main__.py          진입점

tools/                ← C 디지털 트윈
    vfd_pin_trace.c/.h   핀 이벤트 trace 생성 (production scan 재사용)
    vfd_pin_twin.c       스캔 전용 트윈 (512B stdin → trace)
    vfd_system_twin.c    풀스택 트윈 (522B 패킷 → host_link → scan → trace)

tests/                ← C 유닛 + Python 유닛/통합 + 소스계약
```

## 2. 강점 (아키텍처 품질이 뛰어난 부분)

### 2.1 코어/글루 분리가 모범적 ⭐

C 펌웨어에서 **HAL 의존 코드와 무의존 코드의 경계가 선명**하다.

- `vfd_scan.c`, `vfd_host_link.c`, `vfd_delay.c`는 표준 라이브러리만 쓰며, `main.c`가 GPIO 레지스터(`GPIOA->BSRR`)를 직접 건드린다.
- `main.c`는 코어를 호출만 할 뿐, 비즈니스 로직(패킷 처리, 스캔 패킹)이 코어로 역류하지 않는다.
- `VFD_HostProcessByte()`가 HAL 의존을 가진 유일한 외부 진입점이며, UART/USB ISR 바인딩만 남겨둔 설계가 명확하다.
- **`tests/test_firmware_contracts.py`가 소스 계약 테스트로 이 분리를 강제**한다: `main()` 본문에 `vfd_scan_pack_step`/`vfd_scan_emit_frame` 호출 순서, `_Error_Handler`에 `VFD_SafeShutdown()` 포함 여부 등을 정규식으로 검증.

이는 단순한 "분리해 놓았다"가 아니라 **리그레션 시 자동으로 깨지는 구조적 강제**라서 매우 가치 있다.

### 2.2 디지털 트윈의 "치팅 없는 고증 경로" ⭐

가장 인상적인 설계 결정. **TUI/메뉴가 그리는 모든 새 프레임은 실제 production C 코드를 실행한 결과만 표시**한다.

```
Python MvlsbRenderer.snapshot()
  → VfdDisplay.present() (실제 라즈베리파이 경로와 동일)
  → DigitalTwinTransport (SubprocessTransport와 같은 FrameTransport 계약)
  → 522B 패킷 → 실제 C VfdHostLink (더블버퍼, ACK, 43→1 교체)
  → 실제 C vfd_scan (패킹 + emit)
  → 가상 핀 31,272개 이벤트
  → Python decode_pin_trace() 역복원
  → 원본과 1비트 비교 → PASS/FAIL
```

- `DigitalTwinTransport`가 `SubprocessTransport`를 상속해 `_read_response()`만 오버라이드 (템플릿 메서드). 실장 교체 지점이 정확히 한 곳.
- `vfd_pin_twin.c`(스캔만) vs `vfd_system_twin.c`(풀스택)로 테스트 레벨이 분리되어 있고, 둘 다 동일한 `vfd_pin_trace.c`를 재사용.
- **`DIGITAL_TWIN.md`에 "이 테스트가 증명하는 것 / 증명하지 못하는 것"이 명시**되어 있어, 검증 범위에 대한 오해 방지.

### 2.3 InputSource 추상화가 스펙과 코드에 일관되게 구현됨 ⭐

```
InputSource(ABC)  ← 교체 가능한 입력 부품 약속
    .poll() -> List[InputEvent]
        ├── TkinterSource   (프로덕션: 마우스 버튼 → FIFO 큐 → drain)
        ├── FakeInputSource (테스트: 이벤트 리스트 순차 소비)
        └── (예정) GpioSource (물리 버튼)
```

- `MenuModel`은 `InputEvent`만 받고 소스가 누구인지 모른다 → 의존성 역전이 제대로 됨.
- `TkinterSource`가 콜백 기반(Tkinter)과 폴링 기반(메뉴 루프) 사이의 간극을 내부 `deque`로 해소하는 것이 스펙 4.1.2에 정확히 문서화되어 있고, `test_menu_tk_source.py`가 FIFO 순서 보존을 검증.
- `test_menu_input.py`의 `FakeInputSource`로 Tkinter 없이 메뉴 전이를 검증하는 테스트가 존재 → **교체 가능성이 코드로 증명**됨 (스펙 성공 기준 6).

### 2.4 FrameTransport 프로토콜 (구조적 타이핑)

`display.py`의 `FrameTransport`가 `typing.Protocol`로 정의되어, transport 구현체가 명시적 상속 없이 계약을 만족하면 주입 가능하다. `SubprocessTransport`와 `DigitalTwinTransport` 모두 이 계약을 만족.

### 2.5 호스트 링크의 통신 신뢰성 설계

- 더블버퍼 + 43→1 경계에서만 atomic swap (티어링 방지)
- 시퀀스 기반 idempotency (동일 시퀀스+동일 페이로드 → OK, 재스테이징 안 함)
- BUSY 백프레셔 + CRC_ERROR 재시도
- 매직 바이트 동기화 (노이즈 후 재동기)
- `_Static_assert`로 RAM 예산(1080바이트)과 패킷 크기 고정 보장

이 모든 것이 `docs/HOST_PROTOCOL.md`에 단일 진실 원천으로 문서화되어 있고, C와 Python 양쪽에 대칭 구현이 존재.

## 3. 발견된 문제

### 🔴 심각도: 높음

#### H1. `twin.py`가 단일 파일에 7개 관심사 혼재 (710줄)

`twin.py` 하나가 다음을 모두 담당:
1. `DigitalTwinTransport` (transport 계층)
2. `DigitalTwinResult` 데이터 클래스
3. `decode_pin_trace()` + `_reconstruct_frame()` (핀 trace 검증 엔진)
4. `render_tui()` + `_half_block_rows()` + `_braille_rows()` (TUI 렌더링)
5. `render_border_loader_frame()` + `_draw_ascii_art()` + `border_loader_position()` (데모 콘텐츠)
6. `_animate_border_loader()` (애니메이션 루프)
7. `main()` (CLI 진입점 + argparse)

**문제:** 핀 trace 검증 로직(`decode_pin_trace`, ~150줄)은 핵심 도메인 로직인데, TUI 렌더링/데모 콘텐츠/CLI 파서와 같은 모듈에 있어 재사용성과 테스트 격리성이 떨어진다. `menu/presenter.py`가 `twin.py`에서 `DigitalTwinTransport`와 `DigitalTwinError`만 필요함에도 전체 모듈을 import해야 한다.

**권장:** 최소한 다음 3개로 분리
- `twin/transport.py` → `DigitalTwinTransport`, `DigitalTwinResult`, `DigitalTwinError`
- `twin/decoder.py` → `decode_pin_trace`, `_reconstruct_frame`, 핀 이벤트 상수
- `twin/cli.py` → `render_tui`, 데모 렌더링, `main()`

#### H2. `menu/render.py`의 폰트 경로가 `__file__` 기반 하드코딩

```python
_FONT_PATH = os.path.join(os.path.dirname(os.path.dirname(__file__)), "assets", "Galmuri7.ttf")
```

- 패키지가 wheel/egg로 설치되거나 zipapp로 묶이면 깨질 수 있는 패턴.
- 같은 리포의 `twin.py`는 이미 `importlib.resources`를 사용 중 (`load_ascii_art_asset`):
  ```python
  asset_path = resources.files(__package__).joinpath("assets").joinpath(name)
  ```
- **리포 내에서 자산 로딩 방식이 불일치** → 유지보수 혼란.

**추가:** `Galmuri7.ttf`는 `assets/`에 존재하지만 `pyproject.toml`의 `package-data`에는 `*.txt`만 등록되어 있어 **폰트 파일이 wheel에 누락**될 수 있다.

**권장:** `render.py`를 `importlib.resources`로 통일하고, `pyproject.toml`에 `*.ttf` 추가.

### 🟡 심각도: 중간

#### M1. `MenuApp`이 View + Controller 역할 혼재 (엄격한 MVP 위반)

`app.py`의 `MenuApp`이:
- **Controller 역할:** `tick()`에서 입력 소비 → `model.handle_input()` → `model.tick()` → `presenter.present()` 순서 제어
- **View 역할:** `_draw_frame()`에서 Canvas에 4096개 사각형 그리기, 상태 라벨 갱신

엄격한 MVP라면 View(캔버스/라벨 위젯 소유 + 표시만)와 Controller(루프/입력/present 조율)가 분리되어야 한다. 다만 현재 규모(142줄)에서는 감내 가능한 수준이며, 스펙에서도 이 패턴을 의도적으로 선택한 것으로 보인다.

**영향:** 메뉴가 복잡해지면(모드 추가, 애니메이션, 상태 표시 확장) `MenuApp`이 비대해질 위험.

#### M2. `MenuPresenter`가 `DigitalTwinTransport`를 하드코딩 생성

```python
class MenuPresenter:
    def __init__(self, engine: str, ...):
        self._transport = DigitalTwinTransport([engine], timeout=2.0)
```

스펙 4.4는 "나중에 `SubprocessTransport`로 교체하기만 하면 끝"이라고 서술하지만, 실제로는 presenter가 transport를 **직접 생성**하므로, 실기 전환 시 `MenuPresenter` 코드를 수정해야 한다.

**권장:** transport를 생성자 주입으로 변경:
```python
def __init__(self, transport: FrameTransport, renderer=None):
```
그러면 `MenuApp`에서 `DigitalTwinTransport([engine])`을 만들어 주입하고, 실기에서는 `SubprocessTransport([...])`를 주입하면 presenter는 변경 없이 재사용 가능. (이는 `VfdDisplay`가 이미 취하고 있는 패턴이다 — `display.py`는 transport를 주입받는다.)

#### M3. 핀 이벤트 코드 상수가 C/Python 양쪽에 중복 정의

Python `twin.py`:
```python
EVENT_PHASE = 1; EVENT_SIN = 2; EVENT_CLK = 3; ... EVENT_END = 9
```

C `vfd_pin_trace.c`:
```c
enum TwinEvent { TWIN_EVENT_PHASE = 1, TWIN_EVENT_SIN = 2, ... TWIN_EVENT_END = 9 };
```

`vfd_pin_trace.h`의 `VFD_PIN_TRACE_EVENTS_PER_FRAME` 매크로와 Python의 `PIN_EVENTS_PER_FRAME` 계산식도 중복. 현재는 수동으로 일치하지만, 어느 한쪽이 변경되면 조용히 깨진다.

**완화 요인:** `test_twin.py` / `test_pin_twin.py` / `test_system_twin.py` 통합 테스트가 실제로 C 트윈을 실행해 교차 검증하므로, 불일치는 테스트 단계에서 발각된다. 하지만 방어막이 테스트에만 의존한다는 점은 아키텍처적 약점.

**권장:** 코드젠 스크립트로 C 헤더에서 Python 상수를 생성하거나, 최소한 `_Static_assert`/런타임 assert로 교차 검증 추가.

#### M4. 프로토콜 매직 넘버 3곳 중복

`MAGIC = b"VF"`, `PROTOCOL_VERSION = 1` 등이:
- Python `protocol.py`
- C `vfd_host_link.h` (`VFD_HOST_MAGIC_0 = 0x56u` ...)

양쪽에 독립 정의. 다행히 `test_cross_language.py`가 실제 C peer를 띄워 교차 검증하지만, 구조적으로는 DRY 위반.

#### M5. `MenuApp._draw_frame`의 Canvas 갱신이 매 프레임 전체 재생성

```python
self._canvas.delete("all")
for y in range(_HEIGHT):
    for x in range(_WIDTH):
        ... self._canvas.create_rectangle(...)
```

20fps로 4096개 사각형을 매번 삭제+재생성. 이는 성능 문제이기도 하지만 **아키텍처 관점**에서는 View가 픽셀 버퍼를 캐싱하지 않고 무상태로 매번 리빌드한다는 설계 문제.

**권장:** 픽셀 상태를 캐싱하고 변경된 셀만 갱신하거나, `PhotoImage.put()`으로 한 번에 blit.

### 🟢 심각도: 낮음

#### L1. 데모 전용 C 파일이 프로덕션 빌드 경로에 혼재

`vfd_framebuffer.c`(정적 데모 이미지), `font.c`(데모 폰트 배열), `GT20L_Font.c`(데모 폰트 blitter)는 `main.c`의 `render_supplied_demo()`에서만 쓰이는 데모 자산이다. 그런데 `Makefile`의 `CORE_SOURCES`에 포함되어 있고, `firmware/stm32f0/`에 코어 파일들과 나란히 있다.

README에서는 명확히 구분해서 설명하지만, 디렉토리 구조만 보면 코어와 데모의 구분이 모호하다.

**권장:** `firmware/stm32f0/demo/` 서브디렉토리로 이동하거나, 파일명 접두사(`demo_`)로 구분.

#### L2. `MenuApp` 매직 넘버가 `protocol.py` 상수와 중복

```python
_WIDTH = 128   # protocol.py의 FRAME_WIDTH와 동일
_HEIGHT = 32   # protocol.py의 FRAME_HEIGHT와 동일
```

`from ..protocol import FRAME_WIDTH, FRAME_HEIGHT`로 해결 가능한 중복.

#### L3. `presenter.py`의 타입 힌트 불일치

```python
def _draw_frame(self, ..., stats: Optional[dict]) -> None:
```

`dict` 대신 `Dict[str, Any]` 사용 권장 (나머지 모듈은 일관되게 `typing.Dict` 사용 중).

#### L4. `ScreenKind`과 `_MAIN_TARGETS` 리스트의 동기화가 암묵적

```python
_MAIN_ITEMS = 3  # model.py
_MAIN_TARGETS = [ScreenKind.MUSIC, ScreenKind.GAME, ScreenKind.SETTINGS]  # model.py
_MAIN_ITEMS = ["MUSIC PLAYER", "MINI GAME", "SETTINGS"]  # render.py
```

세 곳의 "3개 항목"이 서로 다른 형태로 정의되어 있다. 항목 추가 시 세 곳을 모두 손봐야 하며, 하나라도 빠지면 조용히 잘못 동작.

**권장:** 단일 `MenuItem(kind, label)` 데이터 구조로 통합.

#### L5. `MenuModel` 인덱스 랩어라운드 음수 연산

```python
self._index = (self._index - 1) % _MAIN_ITEMS  # Python은 음수 모듈로가 양수 반환
```

Python에서는 안전하지만, 향후 다른 언어로 포팅하거나 임베디드 C로 메뉴를 옮길 때 음수 모듈로가 함정. 주석 명시 권장.

## 4. 계층 간 경계 평가

### Firmware C ↔ Python 호스트 스택: ✅ 매우 깔끔

- **경계 매체:** 522바이트 바이너리 패킷 + 9바이트 ACK (문서화됨: `HOST_PROTOCOL.md`)

- **유일한 약점:** 매직 넘버 중복 정의 (M4), 핀 이벤트 코드 중복 (M3).

### Python 호스트 스택 ↔ 디지털 트윈(tools/): ✅ 깔끔

- **경계 매체:** `FrameTransport` 프로토콜 (구조적 타이핑)

### 메뉴 MVP 내부: 🟡 양호하나 개선 여지

- **Model → View 분리:** ✅ `MenuModel`은 순수 상태머신, VFD/Tkinter 무의존.

### 1.3 CRC-16/CCITT-FALSE 알고리즘 2개 사본

C `firmware/stm32f0/vfd_host_link.c:21-48`의 `crc16_update`/`vfd_host_link_crc16` 와 Python `src/mn12832l/protocol.py:49-60`의 `crc16_ccitt`는 **동일한 알고리즘**이다.

C (`vfd_host_link.c:21-34`):
```c
crc = (uint16_t)(crc ^ (uint16_t)((uint16_t)byte << 8u));
for (bit = 0u; bit < 8u; ++bit) {
    if ((crc & 0x8000u) != 0u) {
        crc = (uint16_t)((uint16_t)(crc << 1u) ^ 0x1021u);
    } else {
        crc = (uint16_t)(crc << 1u);
    }
}
```

Python (`protocol.py:52-59`):
```python
crc ^= value << 8
for _ in range(8):
    if crc & 0x8000:
        crc = ((crc << 1) ^ 0x1021) & 0xFFFF
    else:
        crc = (crc << 1) & 0xFFFF
```

초기값 `0xFFFF`, 다항식 `0x1021`, 표준 벡터 `"123456789" → 0x29B1` 까지 동일하게 검증된다:
- C: `test_vfd_host_link.c:94-99` `test_crc_standard_vector`
- Python: `test_protocol.py:19-20` `test_crc16_ccitt_false_standard_vector`

**권장:** 알고리즘 자체는 언어 간 복붙이 불가피하지만, 표준 벡터 테스트를 **공통 데이터셋**(`tests/fixtures/crc_vectors.txt`)으로 만들어 양쪽이 같은 벡터를 검증하도록 통일. 현재는 각자 `"123456789"` 문자열을 하드코딩.

### 1.4 핀 트레이스 이벤트 코드 1~9 (C enum ↔ Python 상수)

C `tools/vfd_pin_trace.c:3-13`의 `enum TwinEvent` 와 Python `src/mn12832l/twin.py:45-53`의 모듈 상수가 **1:1로 완전히 동일**하다.

| 값 | C (`vfd_pin_trace.c`) | Python (`twin.py`) |
|---|---|---|
| 1 | `TWIN_EVENT_PHASE` | `EVENT_PHASE` |
| 2 | `TWIN_EVENT_SIN` | `EVENT_SIN` |
| 3 | `TWIN_EVENT_CLK` | `EVENT_CLK` |
| 4 | `TWIN_EVENT_GAP` | `EVENT_GAP` |
| 5 | `TWIN_EVENT_BLANK` | `EVENT_BLANK` |
| 6 | `TWIN_EVENT_LAT` | `EVENT_LAT` |
| 7 | `TWIN_EVENT_EF` | `EVENT_EF` |
| 8 | `TWIN_EVENT_HV` | `EVENT_HV` |
| 9 | `TWIN_EVENT_END` | `EVENT_END` |

`TWIN_EVENT_` 접두사만 빼면 숫자 값과 순서까지 동일하다. C 트윈이 emit한 바이너리를 Python이 decode하므로 **어느 한쪽 값이 바뀌면 트윈 검증이 전부 깨진다**.

추가로 핀 트레이스 헤더 `"VFDTPIN1"` 도 중복:
- C `vfd_pin_trace.c:56-58` (배열 리터럴)
- Python `twin.py:33` `TRACE_HEADER = b"VFDTPIN1"`

그리고 `VFD_PIN_TRACE_EVENTS_PER_FRAME` 산식이 두 언어에서 각각 기술:
- C `vfd_pin_trace.h:11-15`: `7u + VFD_SCAN_PHASES * (1u + 3u*(PIXEL+GRID) + 1u + 4u + 1u) + 4u`
- Python `twin.py:40-42`: `7 + SCAN_PHASES * (1 + BITS_PER_PHASE*3 + 1 + 4 + 1) + 4`

C는 `_Static_assert(VFD_PIN_TRACE_EVENTS_PER_FRAME == 31272u, ...)` (`vfd_pin_trace.c:21-22`)로 리터럴 31272를 고정하고, Python은 `PIN_EVENTS_PER_FRAME`를 계산한 뒤 `decode_pin_trace`에서 결과값을 비교하므로 우연히 일치하고는 있으나, 산식 자체가 독립 사본이다.

**권장:** 이벤트 코드와 헤더 문자열을 단일 소스(예: `tools/vfd_pin_trace.h`에 `#define` + X-Macro)로 두고, Python은 코드젠된 매핑을 import. 또는 최소한 `test_twin.py`에 양쪽 값이 일치함을 검증하는 교차 테스트 추가(현재는 round-trip 결과만 검증).

### 1.5 MVLSB 픽셀 ↔ 바이트 변환 공식

픽셀 `(x, y)` → 바이트 인덱스 `(y // 8) * WIDTH + x`, 비트 마스크 `1 << (y % 8)` 공식이 **6곳**에 반복된다.

Python:
- `src/mn12832l/twin.py:170` `_reconstruct_frame` — `byte_index = (row // 8) * FRAME_WIDTH + base_column + source; frame[byte_index] |= 1 << (row % 8)`
- `src/mn12832l/twin.py:368-369` `_pixel` — `frame[(y // 8) * FRAME_WIDTH + x] & (1 << (y % 8))`
- `src/mn12832l/menu/app.py:100-104` — `byte_row = y // 8; bit = y % 8; frame[byte_row * _WIDTH + x] & (1 << bit)`
- `tests/python/test_twin.py:24-25` `_pixel` — `frame[(y // 8) * 128 + x] & (1 << (y % 8))` (★`FRAME_WIDTH` 대신 매직넘버 `128` 사용★)

C:
- `firmware/stm32f0/vfd_scan.c:45-46` — `page = row / 8u; mask = 1u << (row % 8u)`
- `firmware/stm32f0/GT20L_Font.c:23,52` — `first_page = y / 8u; offset = y % 8u`
- `tests/test_vfd_scan.c:140-141` — `framebuffer[row / 8u][base_column + source] = 1u << (row % 8u)`

문서:
- `docs/HOST_PROTOCOL.md:11` — `byte (y / 8) * 128 + x, bit 1 << (y % 8)`

이 공식은 7번째 사본(문서 포함)까지 나온다. 특히 `tests/python/test_twin.py:25`는 `FRAME_WIDTH` 상수 대신 매직넘버 `128`을 직접 적어, `protocol.py`의 상수와 동기화되지 않는 위험을 안는다.

**권장:** Python에 `protocol.py` 수준의 `pixel_byte_index(x, y)` / `pixel_bit_mask(y)` 헬퍼를 두고 모든 호출처가 이를 사용. C도 인라인 함수 `vfd_pixel_index(page, x)` 등으로 통일 가능(현재는 각 함수가 로컬로 계산).

### 1.6 시퀀스 little-endian 인코딩/디코딩

`sequence` 필드를 2바이트 little-endian으로 직렬화하는 패턴:

- C `vfd_host_link.c:78-84` `configure_receive`: `(uint16_t)header[4] | ((uint16_t)header[5] << 8u)`
- C `vfd_host_link.c:125-126` `encode_ack`: `ack_out[4] = sequence & 0xff; ack_out[5] = sequence >> 8`
- Python `protocol.py:80` `sequence.to_bytes(2, "little")`
- Python `protocol.py:127` `int.from_bytes(raw[4:6], "little")`
- C 테스트 `test_vfd_host_link.c:44-45, 88-89` 동일 패턴

### 2.1 `blit_8px_columns` / `blit_16px_columns` 유사 구조

`firmware/stm32f0/GT20L_Font.c:12-77`의 두 함수는 구조가 거의 동일:

### 4.2 C 테스트의 `build_frame_packet` vs 프로덕션 `encode_ack`

`tests/test_vfd_host_link.c:33-53`의 `build_frame_packet`는 프로덕션 C 코드 `vfd_host_link.c:114-132`의 `encode_ack`와 **필드 순서·직렬화 방식이 동일한 패킷 빌더**다. 차이: 테스트는 FRAME 패킷(522바이트)을, 프로덕션은 ACK 패킷(9바이트)을 만든다.

두 함수 모두:
1. 매직 2바이트
2. 버전 1바이트
3. 커맨드 1바이트
4. 시퀀스 2바이트 little-endian
5. (페이로드)
6. CRC 2바이트 little-endian

이 패턴은 또한 Python `protocol.py:76-85`의 `encode_frame`, `protocol.py:97-105`의 `encode_ack`와도 동일하다. 즉 **패킷 직렬화 로직이 4곳(2 C + 2 Python)에서 독립적으로 재구현**된다.

**권장:** 헤더 직렬화 부분(매직+버전+커맨드+시퀀스 = 6바이트)을 C/Python 각각의 `encode_header(sequence, command)` 헬퍼로 추출.

## 1. 메뉴 루프 (`src/mn12832l/menu/app.py::tick`)

### 1.1 루프 구동 방식

- 진입점: `__main__.py::main()` → `MenuApp(root, engine).start()` → `root.mainloop()`.
- 단일 타이머 루프. `start()`가 `root.after(_FPS_MS=50, self.tick)` 한 번 예약하고,
  `tick()` 마지막에서 다시 `self._root.after(50, self.tick)`로 자기 재예약.
  → **20fps(50ms)** 고정.
- 스레드 단일(Tk 메인 스레드). 별도 워커 스레드 없음.

### 1.2 tick() 한 프레임 데이터 흐름

```text
[1] 입력 소비
    TkinterSource.poll()
      └─ list(self._queue) 복사 → self._queue.clear()
         (Tk 버튼 콜백이 deque에 append 한 것을 한 번에 꺼냄)
    ↓ List[InputEvent]
    for ev in events: MenuModel.handle_input(ev)
      └─ ScreenKind 상태 전이만 (데이터 생성 없음, enum 비교)

[2] 시간 전이
    MenuModel.tick(dt)
      └─ BOOT 상태면 boot_elapsed += dt, 2.0초 경과 시 MAIN_MENU로 전이

[3] 스크린 스냅샷
    MenuModel.current_screen()
      └─ Screen(kind, index, boot_elapsed)  ← frozen dataclass 새 객체 (경량)

[4] 프레젠트 (핵심 파이프라인)
    MenuPresenter.present(screen) → PresentedFrame
      자세한 내부 흐름은 §2 참조

[5] 화면 그리기
    _draw_frame(verified_frame, twin_passed, error, stats)
      └─ Canvas.delete("all")
      └─ 128×32 = 4096회 루프: frame[byte_row*128+x] & (1<<bit) 비트 검사
         → on이면 Canvas.create_rectangle(x*6, y*6, ...) 매번 새 Tk 객체
```

### 1.3 메뉴 루프의 데이터 변환 지점

| 단계 | 입력 → 출력 | 변환 내용 | 복사/할당 |
|------|------------|-----------|-----------|
| `poll()` | deque → list | 큐 덤프 | 매 tick `list()` 신규 할당 |
| `handle_input` | InputEvent → 상태 | enum 디스패치 | 없음 |
| `current_screen` | 내부 상태 → Screen | frozen dataclass | 매 tick 새 객체(경량) |
| `draw_screen` | Screen → 512B | Pillow Image 생성 → 텍스트 blit → framebuffer.image() → snapshot() | **매 tick Pillow Image 신규 할당 + 버퍼 복사 2단계** |
| `_draw_frame` | 512B → 픽셀 | MVLSB 디코딩 → Tk rectangle | **매 tick 4096 Tk 객체 생성/파괴** |

## 2. 디지털 트윈 라운드트립 (`presenter.py` → `twin.py` → `vfd_system_twin.c`)

이 루프는 메뉴 루프의 §1.2 [4] 단계 내부에 중첩되어 있다.

### 2.1 presenter.present() 내부 파이프라인

```text
MenuPresenter.present(screen: Screen) → PresentedFrame
│
├─ [a] draw_screen(screen, renderer)  → 512B frame
│      ├─ Image.new("1", (128,32), 0)           ← Pillow 캔버스 신규 할당
│      ├─ ImageDraw.Draw(image).text(...)        ← Galmuri7 폰트 blit
│      ├─ renderer.load_image(image)
│      │      └─ adafruit_framebuf.FrameBuffer.image()  ← Pillow → 512B bytearray 복사
│      └─ renderer.snapshot()
│             └─ bytes(self._buffer)             ← bytearray → bytes (불변 사본)
│
├─ [b] VfdDisplay.present(frame: 512B)
│      ├─ payload = bytes(frame)                 ← 이미 bytes여도 한 번 더 복사 (방어)
│      ├─ dedup: payload == self._last_frame → 같으면 전송 생략 (sent=False)
│      ├─ encode_frame(payload, sequence)
│      │      ├─ header = MAGIC + ver + cmd + seq(2) + len(2)   (8B)
│      │      ├─ body = header + payload          ← 결합 (새 bytes)
│      │      └─ body + crc16(body)               ← 최종 522B (또 새 bytes)
│      └─ 전송 루프 (retry: BUSY/CRC_ERROR 시 최대 2회)
│             └─ transport.request(packet: 522B) → ack: 9B
│
├─ [c] DigitalTwinTransport._read_response()
│      ├─ read ACK 9B → decode_ack
│      ├─ status==OK 이면 추가로 PIN_TRACE_BYTES(62552B) 수신
│      ├─ source_frame = packet[8:520]            ← memoryview 슬라이스 (0-copy)
│      └─ decode_pin_trace(trace, source_frame)
│             ├─ 31272개 이벤트 × 2B 순회, 가상 시프트 레지스터 모사
│             ├─ _reconstruct_frame(phase_bits) → 512B bytearray
│             ├─ source_frame 비교 (다르면 예외로 FAIL 표시)
│             └─ DigitalTwinResult (frozen dataclass)
│
└─ [d] PresentedFrame(verified_frame, twin_passed, stats, error) 반환
```

### 2.2 Python ↔ C 라운드트립 데이터 팽창

```text
Python이 보낸 것:  522 바이트 (8 헤더 + 512 페이로드 + 2 CRC)
C가 돌려준 것:    9 바이트 ACK  +  62552 바이트 핀 트레이스
                                            ─────────────────
                  헤더 8B + 31272 이벤트 × 2B
                  (43 phase × (1 PHASE + 240비트×3 SIN/CLK + 1 GAP + 4 LAT/BLANK + 1 HV))
```

512바이트 프레임이 핀 레벨에서 **약 122배**로 팽창한다. 이는 하드웨어 핀 동작을
비트 단위로 충실히 모사하기 위한 의도적 설계이며, `decode_pin_trace`가 이를 다시
512바이트로 역복원한다.

### 2.3 C 바이너리 내부 데이터 흐름 (`vfd_system_twin.c::main`)

```text
[영구 루프 — stdin EOF까지]
  read_packet(packet[522])                    ← fread로 정확히 522B 읽기
    │
    ├─ process_packet(link, packet)
    │      │
    │      ├─ for i in 0..521:
    │      │      vfd_host_link_feed(link, packet[i], ack)
    │      │        ← 바이트 단위 state machine:
    │      │          - 헤더 8B 파싱 (magic/ver/cmd/seq/len)
    │      │          - 페이로드 512B → 백 버퍼(buffers[front^1]) 직접 기록
    │      │          - CRC 2B 누적 → 검증 → ACK 9B 인코딩
    │      │
    │      ├─ fwrite(ack, 9B) → stdout
    │      │
    │      └─ if ack==OK:
    │            vfd_host_link_swap_if_pending(link, NULL)
    │              ← front_index ^= 1  (더블버퍼 포인터 교환, 0-copy)
    │            vfd_pin_trace_write(stdout, front_buffer)
    │
    └─ fflush(stdout)

vfd_pin_trace_write(stream, framebuffer[4][128]):
  fwrite("VFDTPIN1", 8B)
  초기 핀 상태 7 이벤트 (SIN/CLK/LAT/BLANK/EF/HV/EF)
  for phase in 1..43:
    emit PHASE(phase)
    vfd_scan_pack_step(framebuffer, phase, scan_frame[30])
      ← framebuffer의 3열 × 32행을 6lane으로 재배열 + 48bit grid selector → 30B
    vfd_scan_emit_frame(scan_frame, callbacks)
      for bit in 0..239:
        if bit==192: gap callback
        write_bit(value):
          emit SIN(value); emit CLK(0); emit CLK(1)   ← 3 이벤트/비트
    emit BLANK(1); LAT(1); LAT(0); BLANK(0)           ← 4 이벤트
    state_advance → emit HV(hv_enabled)                ← 1 이벤트
  종료 4 이벤트 (BLANK/HV/EF/END)
  → 총 31272 이벤트 × 2B = 62552B
```

### 2.4 디지털 트윈의 정체성 경계

문서 `docs/DIGITAL_TWIN.md`가 명시하듯, 트윈은 "Python이 원본 그림을 그대로
출력하는 눈속임"이 아니다. 교체되는 부분은 **하드웨어 경계 어댑터뿐**이며:

- `VfdDisplay`, `FrameTransport` 계약, C `VfdHostLink`, C `vfd_scan` core는
  실장 경로와 **동일 코드**를 공유한다.
- `SubprocessTransport`(파이프) ↔ `serial_bridge.py`(UART/USB)만 교체된다.

## 3. C 펌웨어 메인 루프와 ISR (`firmware/stm32f0/`)

### 3.1 두 루프의 분리: ISR vs 메인 루프

```text
┌─────────────────────────────────────────────────────┐
│ TIM14 인터럽트 (312.5µs 주기, 우선순위 기반 선점)     │
│                                                     │
│  TIM14_IRQHandler():                                │
│    HAL_TIM_IRQHandler(&htim14)   ← HAL 플래그 클리어 │
│    vfd_scan_due = 1u              ← volatile 1바이트 │
│                                                     │
│  ※ ISR은 플래그 설정만. 스캔 작업은 메인 루프로 연기. │
└─────────────────────────────────────────────────────┘
                        │ (선점 종료 후)
┌─────────────────────────────────────────────────────▼─┐
│ 메인 루프 (main.c::main 의 while(1))                  │
│                                                       │
│  vfd_scan_event_take():                               │
│    __disable_irq()                                    │
│    due = vfd_scan_due; vfd_scan_due = 0               │
│    if (was_enabled) __enable_irq()                    │
│    ← PRIMASK 저장/복원 기반 임계구역 (재귀 인터럽트 안전)│
│                                                       │
│  if (!due) continue;  ← 바쁜 대기 (저전력 미사용)      │
│                                                       │
│  [한 타이머 틱당 수행되는 스캔 1상]                     │
│  1. vfd_latch_previous_frame(unblank=true)            │
│       BLANK high → 17us 대기 → LAT high → 3us          │
│       → LAT low → 255ns → BLANK low (화면 재개)        │
│  2. vfd_scan_emit_frame(scan_frame, GPIO 콜백)         │
│       30B 스캔프레임의 240비트를 MSB-first로 비트뱅:    │
│         vfd_write_scan_bit(bit):                       │
│           SIN = bit; CLK low; CLK high                 │
│         192번째 비트 후 gap hook (13us 대기)            │
│  3. vfd_scan_state_advance()                           │
│       phase++; 43 초과 시 phase=1, HV 펄스 2틱         │
│  4. if phase==1: swap_if_pending()  (프레임 경계 스왑) │
│  5. hv_enable/disable (GPIOF)                          │
│  6. vfd_scan_pack_step(front, phase, scan_frame)       │
│       ← 다음 틱에 쓸 30B를 미리 준비                    │
└───────────────────────────────────────────────────────┘
```

### 3.2 펌웨어 데이터 변환 지점

| 지점 | 변환 | 비고 |
|------|------|------|
| `vfd_scan_pack_step` | `front_buffer[4][128]`의 3열 → `scan_frame[30]` | 6lane 홀수/짝수 재배열 + 48bit grid |
| `vfd_scan_emit_frame` | 30B → 240비트 스트림 | MSB-first, 192번째 비트 후 gap |
| `vfd_write_scan_bit` | 비트 → GPIO BSRR/BRR 레지스터 | 메모리 맵 직접 쓰기 (0-copy) |
| `vfd_host_link_feed` | UART 바이트 → 백 버퍼 | 스트리밍, 1바이트씩 |

### 3.3 호스트 링크 수신 경로 (별도 엔트리포인트)

`VFD_HostProcessByte(byte, ack_out)`는 `main.c`의 `while(1)`에서 직접 호출되지
않는다. 이 함수는 보드 포팅 시 UART/USB CDC ISR 또는 DMA 콜백이 큐에 넣은 바이트를
**메인 루프**에서 꺼내 호출하도록 의도된 진입점이다(`docs/HOST_PROTOCOL.md`의
"STM32 board glue still required" 절 참조). 현재 번들에는 해당 주변장치 바인딩이
포함되어 있지 않다.

### 3.4 TIM14 주기 계산

- HSI 8MHz × PLL12 = **48MHz** SYSCLK
- TIM14: prescaler `100-1`, period `150-1`
- 주파수 = 48MHz / 100 / 150 = **3200Hz** → **312.5µs** 마다 스캔 1상
- 43상 × 312.5µs = **13.44ms**/풀 프레임 (약 74Hz 리프레시)

## 4. 직렬 프로토콜 (`protocol.py` ↔ `vfd_host_link.c`)

### 4.1 프레임 구조

```text

│ 오프셋 │  0   │  2   │   3     │     4        │       6          │   520   │
├────────┼──────┼──────┼─────────┼──────────────┼──────────────────┼─────────┤
│ 크기   │  2   │  1   │   1     │     2        │       2          │  512    │  2  │
│ 내용   │"VF"  │ ver  │ cmd=01  │ sequence     │ length=512(0x200)│ MVLSB   │ CRC │
└────────┴──────┴──────┴─────────┴──────────────┴──────────────────┴─────────┘
                                                                       ↑
                                CRC-16/CCITT-FALSE (초추 0xFFFF, 다항 0x1021)

ACK 패킷 (9 바이트)
┌────────┬──────┬──────┬─────────┬─────────┬────────┬─────────┐
│ 오프셋 │  0   │  2   │   3     │   4     │   6    │    7    │
├────────┼──────┼──────┼─────────┼─────────┼────────┼─────────┤
│ 크기   │  2   │  1   │   1     │   2     │   1    │    2    │
│ 내용   │"VF"  │ ver  │ ack=80  │ seq     │ status │   CRC   │
└────────┴──────┴──────┴─────────┴─────────┴────────┴─────────┘
```

### 4.2 양쪽 구현 대칭성

| 항목 | Python (`protocol.py`) | C (`vfd_host_link.c`) |
|------|------------------------|------------------------|
| 매직 | `b"VF"` (0x56 0x46) | `VFD_HOST_MAGIC_0/1` (0x56/0x46) |
| 버전 | `PROTOCOL_VERSION = 1` | `VFD_HOST_PROTOCOL_VERSION = 1u` |
| CRC | `crc16_ccitt()` (바이트 루프) | `crc16_update()` (바이트 루프) |
| 인코딩 | `encode_frame()` 일괄 패킹 | `vfd_host_link_feed()` 바이트 단위 스트리밍 |
| 디코딩 | `decode_ack()` 일괄 언패킹 | ACK는 feed 내부에서 인코딩 |

Python은 패킷 단위(블록), C는 바이트 단위(스트림)로 처리한다. 이 비대칭은
실제 UART/USB 수신이 바이트 스트림이기 때문이며, 호스트 쪽은 이미 완성된
바이트열을 다루므로 정당하다.

### 4.3 ACK 상태와 재시도 시맨틱

```text
OK(0)         → 프레임 적재 성공 (또는 동일 시퀀스 중복 수신 = idempotent)
CRC_ERROR(1)  → 체크섬 실패      ─┐ 호스트가 재전송 대상
BUSY(5)       → 다른 프레임 대기 중 ─┘ (VfdDisplay._RETRYABLE, 최대 2회)
VERSION_ERROR(2), COMMAND_ERROR(3), LENGTH_ERROR(4) → 영구 거부
```

`VfdDisplay.present`는 `BUSY`/`CRC_ERROR`를 `retry_limit=2`까지 동일 시퀀스로
재전송한다. 매 10ms 간격.

### 4.4 전송 계층 어댑터 2종

```text
[실장]  Python ──(522B)──▶ serial_bridge.py ──▶ pyserial ──▶ STM32 UART
                             (stdin→serial→stdout ACK 프록시, 영구 프로세스)

[트윈]  Python ──(522B)──▶ DigitalTwinTransport ──▶ subprocess stdin/stdout
                             ──▶ vfd_system_twin 바이너리
```

두 어댑터 모두 동일한 `FrameTransport` 프로토콜(`open/request/close`)을 구현하므로
상위 `VfdDisplay`는 어느 쪽인지 알지 못한다.

## 5. 루프별 불필요한 직렬화·잉여 복사 분석

> 아래는 데이터 흐름 관점에서 관찰된 복사/할당 지점이다. 최적화 권고가 아닌
> 사실 기술이며, 대부분은 불변성 보장 또는 방어 코드로서 정당하다.

### 5.1 메뉴 루프 (`tick`)

| 위치 | 내용 | 정당성 |
|------|------|--------|
| `draw_screen` 매 tick `Image.new` | Pillow 캔버스 재할당 | `lru_cache`된 폰트 외 매번 새 이미지. 더티 리전 방식이 아니라 전체 재그림. |
| `renderer.load_image` → `snapshot()` | Pillow → framebuffer bytearray → bytes | 2단계 복사. `adafruit_framebuf.image()`가 내부 복사, `bytes()`가 불변 사본. |
| `TkinterSource.poll()` | `list(deque)` + `clear` | 매 tick 리스트 할당. 이벤트 수가 적어 경미. |
| `_draw_frame` 4096 `create_rectangle` | 매 tick Tk 객체 생성/`delete("all")` | `PhotoImage`.put() 기반 스캔라인 갱신보다 Tk 객체 오버헤드가 큼. |

### 5.2 디지털 트윈 라운드트립

| 위치 | 내용 | 정당성 |
|------|------|--------|
| `VfdDisplay.present`: `payload = bytes(frame)` | 이미 `bytes`여도 한 번 더 복사 | `bytearray`/`memoryview` 입력 방어. dedup 비교용 불변 확보. |
| `encode_frame`: `body = header + payload`, `return body + crc` | 522B 조립 시 2회 버퍼 결합 | 512B 크기라 미미. `bytearray`+`extend`로 줄일 수 있으나 가독성 트레이드오프. |
| `decode_pin_trace`: `trace = bytes(trace)`, `source_frame = bytes(...)` | 입력 방어 복사 | `BytesLike` 타입 수용용. 슬라이스는 이미 새 객체이므로 실제 복사는 1회. |
| 핀 트레이스 62552B 매 프레임 파이프 전송 | 512B → 122배 팽창 | **의도적**. 핀 레벨 충실도가 트윈의 존재 이유. |
| `_reconstruct_frame` bytearray → `DigitalTwinResult` bytes | 재구성 버퍼의 불변화 | frozen dataclass 요건. |

### 5.3 C 펌웨어

| 위치 | 내용 | 정당성 |
|------|------|--------|
| `vfd_scan_pack_step` 매 틱 `memset(frame, 0, 30)` + 재팩 | 백 버퍼 → 30B 스캔프레임 | 필수 변환(MVLSB → 6lane 배선). |
| `vfd_host_link` 백 버퍼 직접 기록 | 페이로드를 임시 버퍼 없이 백 버퍼에 스트리밍 | **0-copy**. 양호. |
| `swap_if_pending`: `front_index ^= 1` | 포인터 교환만, 데이터 복사 없음 | **0-copy 더블버퍼링**. 양호. |

### 5.4 프로토콜

| 위치 | 내용 | 정당성 |
|------|------|--------|
| Python `encode_frame` 다단계 bytes 결합 | header+payload, body+crc | 위 5.2와 동일. |
| C `vfd_host_link_feed` 바이트 단위 CRC 누적 | 512바이트를 1바이트씩 `crc16_update` | 스트리밍 수신 구조상 필수. 블록 CRC보다 효율적. |
| `serial_bridge.py`: `_read_exact` → `bytearray.extend` | 프레임 조립 | 파이프 특성상 불가피. |

### 5.5 종합 평가

- **불필요한 직렬화/역직렬화**: 발견되지 않음. 모든 경로는 이진 프레임(512B)의
  단순 복사 또는 프로토콜 헤더/CRC 부착이다. JSON/protobuf/Base64 등의 텍스트
  인코딩 오버헤드는 전혀 없다.
- **잉여 복사**: `VfdDisplay.present`의 `bytes(frame)` 1회, `encode_frame`의
  버퍼 결합 2회가 기술적으로 존재하지만, 512B 크기이므로 무시 가능 수준이다.
- **가장 큰 데이터 흐름 비용**: 디지털 트윈의 핀 트레이스(62552B/프레임)이며,
  이는 설계 의도에 따른 것이다.
- **구조적 우수 지점**: C 펌웨어의 더블버퍼 포인터 스왑(0-copy), 바이트 단위
  스트리밍 호스트 링크, `SubprocessTransport`의 `os.read`/`os.write` 직접
  사용(버퍼링 최소), `FrameTransport` 프로토콜로 인한 트윈/실장 경로 공유.

### 4.3 구조적 강점 (변경 불필요)

3개 리뷰가 모두 인정한 모범 사례:

- ✅ **코어/글루 분리** (C): HAL 의존 경계 선명, 소스 계약 테스트로 강제
- ✅ **디지털 트윈 충실도**: production C 코드를 그대로 재실행 (시뮬레이션 전용 코드 아님)
- ✅ **InputSource ABC 추상화**: FakeInputSource로 교체 가능성 증명됨
- ✅ **FrameTransport 프로토콜**: 구조적 타이핑으로 트윈/실장 경로 공유
- ✅ **C 더블버퍼 0-copy**: `front_index ^= 1` 포인터 교환
- ✅ **호스트 링크 신뢰성**: 더블버퍼 + 시퀀스 idempotency + CRC 재시도 + 매직 동기화
- ✅ **바이너리 프로토콜**: JSON/protobuf/Base64 오버헤드 전무, 522B 고정 프레임
